# Separate rules, strategies and oracles in the solver

The rewriting core `@math-blocks/solver` needs is **strategy-controlled term rewriting with tracing**, not equality saturation and not completion. It has three parts. First, a library of small, declarative, named rules (pattern, guard, template or function, and a message drawn from the existing `Step['message']` union). Second, a small TypeScript strategy-combinator layer that makes today's hidden control loop explicit and turns labelled sub-strategies into `substeps`. Third, a separate equivalence oracle (a canonical polynomial form plus randomized numeric evaluation, with an optional small TypeScript e-graph later) that checks steps, recognizes what a student did and picks target forms, but never writes the steps itself. This is the design shared by the Ideas tutoring framework, Rubi, CortexJS Compute Engine and Wolfram|Alpha's step-by-step solutions. Wolfram|Alpha says outright that its steps do not trace its fast CAS algorithms; they come from a separate pedagogical rule system ([Wolfram|Alpha Blog](https://blog.wolframalpha.com/2009/12/01/step-by-step-math/)). E-graphs are attractive because they never lose a form, but in an n-ary AC algebra domain their weaknesses are serious. AC rules cause combinatorial blowup, explanations come out in proof order rather than teaching order, and no mature JavaScript or TypeScript library exists. That confines them to an oracle role. Geometry changes the picture, though not the recommendation. School geometry is best served by a second engine of the same family: a Datalog-style forward-chaining fact store with union-find and justification records, in the shape of AlphaGeometry's DDAR. Its derivations map directly onto two-column "statement / reason" proofs, and it calls the algebra rewriter for numeric sub-steps. The migration can be incremental and behavior-preserving: first express the current loop as combinators, then wrap the existing transforms as rules, then add a step checker, then convert rules to declarative patterns, and add geometry last.

## The current loop is a strategy with its policy hidden in list order

`simplify()` in `packages/solver/src/simplify/simplify.ts` keeps an ordered array of transforms (18 in the current file: `dropAddIdentity`, `simplifyDivByFrac`, `simplifyMul`, `mulByZeroIsZero`, `distribute`, `distributeDiv`, `collectLikeTerms`, `dropParens`, `evalMul`, `evalAdd`, `reduceFraction`, `mulFraction`, `evalDiv`, `mulToPow`, `multiplyPowers`, `dividePowers`, `removePowOne`, `addNegToSub`). It tries them in order at each numeric node on exit from a post-order traversal, and the first transform to return a `Step` wins. It then retries at the same node up to **10 times**, and an outer loop re-traverses the whole tree up to **10 times** until nothing changes. In combinator terms this is roughly `repeat≤10(bottomup(repeat≤10(t1 <+ t2 <+ … <+ t18)))`, a capped form of SymbolicUtils.jl's `Fixpoint(Postwalk(Fixpoint(Chain)))` ([SymbolicUtils rewrite docs](https://github.com/JuliaSymbolics/SymbolicUtils.jl/blob/master/docs/src/manual/rewrite.md)). The file's comments show that list position carries pedagogical policy. One says to "eval multiplication before mulToPower to avoid (3)(3) -> 3^2". Another puts `addNegToSub` last "so that we don't covert 3 + -(x + 1) to 3 - (x + 1) before distributing." The loop also never re-normalizes a rewritten node's new children; it leaves that to the next outer pass. The order of the emitted steps is therefore an artifact of the loop's structure as much as of rule priority, which makes it hard to predict or test.

The closest public precedent is a warning. Google/Socratic's **mathsteps** is almost a structural twin of this design. It has priority-ordered imperative "searches" (`basicsSearch`, `divisionSearch`, `collectAndCombineSearch`, …), a tree search that returns on the first change, a `stepThrough` fixpoint loop capped at **20 steps** that logs "Potential infinite loop", and a 79-entry `ChangeTypes` enum ([mathsteps stepThrough.js](https://github.com/google/mathsteps/blob/master/lib/simplifyExpression/stepThrough.js); [ChangeTypes](https://github.com/google/mathsteps)). It has no declarative rule layer and was archived in August 2024 ([GitHub google/mathsteps](https://github.com/google/mathsteps)). No source gives the reason it was abandoned, so its archival proves nothing about the design. It does show where the current design leads: a growing collection of hand-coded functions whose interactions are visible only by running them.

## Strategy-controlled rewriting should generate the displayed steps

Every mature rewriting system separates **rules**, which are local rewrites that succeed or fail, from **strategies**, which handle traversal and control. Stratego defines `try(s) = s <+ id`, `repeat(s) = try(s; repeat(s))` and `topdown(s) = s; all(topdown(s))`, with `<+` as left-biased choice ([program-transformation.org](https://program-transformation.org/Stratego/StrategyDefinition.html); [Tom manual](https://tom.loria.fr/soft/release-2.4/manual-2.4/manual008.html)). Maude splits confluent, terminating equations from strategy-controlled rules, and its strategy language adds regular-expression composition and a conditional whose test is itself a strategy ([Maude strategy language, arXiv 2401.07749](https://arxiv.org/pdf/2401.07749)). Kiama shows the Stratego vocabulary working as an embedded library in a host language rather than as a separate language ([Kiama Rewriter](https://javadoc.io/static/com.googlecode.kiama/kiama_2.9.2/1.4.0/org/kiama/rewriting/Rewriter.html)). SymPy's `strategies` module exists for the stated purpose of separating mathematical rules from the algorithms that apply them ([Rocklin, "Strategies"](https://matthewrocklin.com/blog/work/2012/11/07/Strategies)). The research turned up no maintained TypeScript strategy-combinator library. That is weak evidence, but it suggests the solver should write its own, and about fifteen combinators would cover it: `seq`, `choice`, `tryS`, `repeat(s, {max})`, `oncebu`, `oncetd`, `bottomup`, `innermost`, `named`, `guard` and a few traversals.

The strategy most useful for teaching is **`repeat(oncebu(choice(rules)))`**, which emits exactly one `Step` per iteration at one position. mathsteps' main loop has this shape, and it makes every step independently checkable. Phase ordering such as "convert `+ -` to `-` only after distribution" becomes `seq(normalizePhase, cosmeticPhase)` instead of list position. A `named('collect like terms', seq(reorder, factorVar, computeCoeffs))` combinator records its inner steps as `substeps`, reproducing the existing messages "reorder terms so that like terms are beside each other", "factor variable part of like terms" and "compute new coefficients" without special-casing inside the transform.

Rubi shows that this scales. It is a rule-based integrator with about **6,600 rules** (the CortexJS TypeScript port's data file holds **6,574**) that outperforms Maple and Mathematica on a test suite of over 70,000 integrands. It achieves determinism through a decision tree of mutually exclusive side conditions plus a load order its authors call "vitally important", and each step can display its rule and the conditions that held ([Rubi README](https://github.com/RuleBasedIntegration/Rubi); [CortexJS rubi data](https://github.com/cortex-js/compute-engine/tree/main/src/compute-engine/rubi)). The solver's ordering comments are informal side conditions, and they should become explicit guards. CortexJS Compute Engine is the most relevant TypeScript design reference ([compute-engine types](https://github.com/cortex-js/compute-engine/blob/main/src/compute-engine/types-kernel-evaluation.ts); [rules.ts](https://github.com/cortex-js/compute-engine/blob/main/src/compute-engine/boxed-expression/rules.ts)). Its rules carry an `id`, and the trace records `RuleStep {value, because, substeps}`. A `purpose` tag (`simplify`, `transform`, `expand`) puts simplify-rules through a cost gate that discards results which grow the expression. Its conditions are **fail-closed**: an unprovable predicate such as `w ≠ 0` for an unconstrained `w` does not satisfy the guard.

Matching modulo AC is NP-complete in general, but linear patterns, in which each variable appears once, have a polynomial bound ([Benanav, Kapur & Narendran](https://dx.doi.org/10.1007/3-540-15976-2_22)). The solver's n-ary `Add` and `Mul` nodes are already the flattened form that Maude, Mathematica and mathjs build internally ([mathjs simplify.js](https://github.com/josdejong/mathjs/blob/develop/src/function/algebra/simplify.js); [Wolfram Flat](https://reference.wolfram.com/language/ref/Flat.html)), so associativity is handled by the representation. Commutativity should be opt-in per rule through segment (rest) variables matched left to right, as in SymbolicUtils' `~~xs` and CortexJS's `...a`, with a permutation cap. That choice also has a pedagogical advantage: the match reports which terms were brought together, which a "collect like terms" step needs to show. None of the surveyed engines attaches student-facing messages to rules; they all record a rule id and format it afterwards. The solver can do better, because TypeScript can check that a rule's `message` belongs to the `Step` union:

```ts
rule({
  id: 'distribute', message: 'distribute', purpose: 'expand',
  lhs: mul(v('a'), add(seq('terms'))),
  rhs: ({a, terms}) => add(...terms.map(t => mul(a, t))),
  where: ({a}) => !isZero(a),              // fail-closed guard
})
```

Algorithmic transforms such as `collectLikeTerms` and `reduceFraction` (gcd, grouping) should stay as function-valued rules. mathjs and CortexJS both keep this escape hatch, and nothing is gained by forcing them into patterns. mathjs's own engine is a poor fit to adopt directly. It applies each rule everywhere in one pass, has no per-application trace, and converts between binary and n-ary trees around every rule ([mathjs simplify.js](https://github.com/josdejong/mathjs/blob/develop/src/function/algebra/simplify.js)).

## E-graphs earn a place as an oracle, not as the step generator

An e-graph stores equivalence classes of expressions. Equality saturation applies every rule without discarding anything and then extracts a best term, and egg made this fast through deferred rebuilding and pluggable e-class analyses ([egg tutorial](https://docs.rs/egg/latest/egg/tutorials/index.html); [egg paper](https://arxiv.org/pdf/2004.03082)). Several properties fit an algebra domain well. Constant folding and "known nonzero" analyses map directly onto guards like cancelling `x/x` ([hegg README](https://hackage.haskell.org/package/hegg-0.6.0.0/src/README.md)). egglog adds Datalog with lattice merges ([egglog, arXiv 2304.04332](https://arxiv.org/pdf/2304.04332)). Ruler and Enumo synthesize compact rule sets automatically ([Ruler, OOPSLA 2021](https://2021.splashcon.org/details/splash-2021-oopsla/23/Rewrite-Rule-Inference-Using-Equality-Saturation); [Enumo](https://par.nsf.gov/biblio/10510243-equality-saturation-theory-exploration-la-carte)). Herbie's switch to egg made its simplifier about **100× faster** ([Herbie 1.4 notes](https://fpbench.cs.washington.edu/doc/1.4/release-notes.html)).

Four problems keep e-graphs out of the step-generator role. The first is AC. Associativity and commutativity are rules "known to cause combinatorial blowup" ([Rosin, Ullrich & Hack, EGRAPHS 2026](https://compilers.cs.uni-saarland.de/papers/ullrich_egraphs2026-paper17.pdf)), and the field's 2025–2026 answer is native AC containers such as multisets ([UW PLSE egglog containers](https://uwplse.org/2026/02/24/egglog-containers.html); [Zucker, arXiv 2504.14340](https://arxiv.org/abs/2504.14340)). A TypeScript port would need custom AC-canonical hash-consing and a custom matcher. The second is explanations. egg can produce proofs, and FMCAD 2022 made them small with an O(n log n) greedy algorithm ([Flatt et al.](https://repositum.tuwien.at/bitstream/20.500.12708/81325/1/Flatt-2022-Small%20Proofs%20from%20Congruence%20Closure-vor.pdf)), but those proofs optimize size, not readability. They can apply simplifying rules backwards and interleave steps in non-textbook order, and lean-egg reports that reconstructing proofs from them is fiddly ([Equational Theories blueprint](https://teorth.github.io/equational_theories/blueprint/egraphs-chapter.html)). The research found **no published work that turns e-graph explanations into student-facing steps** and no e-graph-based "solve for x". The third is saturation itself. Distribution never saturates, and even Herbie moved to multi-phase rewriting ([UW PLSE Herbie](https://uwplse.org/2024/05/09/Herbie-Numerical-Compiler.html)), which is a strategy by another name. The fourth is tooling. The only TypeScript e-graph is the niche `atsds-egg` ([pkgstats](https://www.pkgstats.com/pkg:atsds-egg)), and egglog's WASM build exposes a text DSL whose size is estimated at several megabytes ([egglog README](https://github.com/egraphs-good/egglog); [DeepWiki, secondary](https://deepwiki.com/egraphs-good/egglog/2.4-python-and-webassembly)).

The proof-assistant pattern resolves this: **search with anything, then replay through small, named, checked rules.** Lean's egg tactic is "partially unsound" but safe, because the kernel checks the reconstructed proof ([Rossel et al.](https://ar5iv.labs.arxiv.org/html/2405.10188)). For math-blocks, an e-graph earns its keep in three places. It can check equivalence where a canonical form is awkward (rational expressions with domain conditions). It can choose targets, for example the simplest form under a tree-cost extraction that is cheap in a browser. And it can audit rules offline. School-algebra expressions have under about 50 nodes, so a few hundred lines of TypeScript (union-find, hash-cons with sorted n-ary children, rebuild, top-down matching) would suffice if it is ever needed. It should be built only after a concrete need appears that the canonical-form oracle cannot meet.

## Tutoring systems use the same strategy to check student steps

The Ideas framework (Heeren, Jeuring and Gerdes, Open Universiteit / Utrecht) is the closest existing design to what math-blocks needs. A domain supplies rules, including **buggy rules**, and a strategy written in a combinator language. Checking a student's sequence of steps then becomes a **parsing problem**: is the sequence a prefix of the language of rule sequences the strategy describes ([Specifying Rewrite Strategies for Interactive Exercises](https://cs.ou.nl/members/bastiaan/StrategiesForExercisesJournal.pdf)). The feedback services are derived from that one artifact. `allfirsts` gives every allowed next step, `onefirst` picks one of them by rule ordering, `derivation` gives a worked solution, and `diagnose` classifies a student step as Expected, Detour, Buggy, NotEquivalent and so on ([Properties of Exercise Strategies, arXiv 1012.5561](https://arxiv.org/pdf/1012.5561)). The exact combinator names and the full set of diagnosis results were not verified against primary text this session. The architecture claims are sourced. A strategy AST interpreted lazily as a stream of `(rule, location, result)` gives math-blocks all of these services, and the `Step` tree falls out of `label` nodes: each label becomes a parent step and the rules inside it become its substeps.

The other tutoring traditions sharpen the design. Lynnette, an equation-solving tutor, was rebuilt from example-tracing behavior graphs into a rule-based tutor "to be more flexible in recognizing students' major and minor solution variations" ([Aleven et al., IJAIED 2016](https://www.cs.cmu.edu/~bmclaren/pubs/AlevenEtAl-CTAT-IJAIED2016.pdf)). That argues for generating the solution space from rules rather than authoring a path for each problem. Model tracers search with correct rules first and add buggy rules one at a time, so that each diagnosis uses as few misconceptions as possible ([US Patent 6634887](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/6634887)). Buggy rules can multiply impractically even in simple domains ([van der Bent et al.](https://webspace.science.uu.nl/~jeuri101/homepage/Publications/DiagnosingBehaviour.pdf)), so the set should stay small and curated: sign errors when moving a term across `=`, distributing to only the first term, dividing only one term, and combining unlike terms. Andes found that students skip and combine primitive steps ([VanLehn et al. 2005](https://www.public.asu.edu/~kvanlehn/distrib/AndesLessonsLearnedForWeb.pdf)), so the checker must accept multi-rule jumps. The 2025 work on combined steps avoids enumerating intermediate states. It searches for rule paths whose final answer matches the student's, and that diagnosed **29.4%** of combined steps, matching teachers **97%** of the time on a 115-step subset ([van der Hoek, Jeuring & Bos](https://arxiv.org/abs/2507.13651)). For equivalence itself, the cheapest robust approach is canonical polynomial form first, with randomized exact-rational evaluation as a fallback. A small open-source checker uses only numeric evaluation to locate the first wrong line ([algebra-step-checker](https://github.com/dguywhoknows/algebra-step-checker)).

The same structure handles step selection and granularity. Published systems prefer ordering to numeric cost ([arXiv 1012.5561](https://arxiv.org/pdf/1012.5561); [Wolfram|Alpha Blog](https://blog.wolframalpha.com/2009/12/01/step-by-step-math/)). The policy therefore has three layers: strategy order as hard preference, a lexicographic tie-break cost (avoid fractions, keep coefficients positive, prefer leftmost position), and, when tracing a student, restarting the strategy from the student's own expression. Granularity "levels" come from always generating the finest-grained step tree and collapsing labelled subtrees for display. Collapsing can be by category (arithmetic, like-terms, inverse operations) or driven by mastery estimates from knowledge tracing, which works per production rule ([ScienceDirect: Cognitive Tutor](https://www.sciencedirect.com/topics/computer-science/cognitive-tutor)). Hint ladders come for free from the same structure, in the general-to-specific order Andes used: first the label of the next sub-strategy, then the rule's message, then the `after` expression.

## Geometry needs a saturating fact engine beside the rewriter

Geometry is where saturation belongs, though as Datalog-style fact saturation rather than an algebra e-graph. Algebraic provers such as Wu's method and Gröbner bases are strong, but their proofs are polynomial manipulation no student can read. GeoGebra exposes them as true/false answers with degeneracy conditions ([Kovács et al., ATCM 2020](https://atcm.mathandtech.org/EP2020/invited/21786.pdf)), which suits a hidden verifier. Readable proofs come from the Chou–Gao–Zhang **deductive database** approach: forward-chain a fixed rule set to a fixpoint ([JAR 2000](https://unpaywall.org/10.1023%2FA%3A1006171315513)). AlphaGeometry's symbolic engine follows that approach. Its DDAR combines **43 rules over 21 predicates** (`para`, `perp`, `cong`, `cyclic`, `eqangle`, `simtri`, `contri`, …) with an algebraic module, and its open-source output already numbers each proof step and cites premises like a two-column proof ([AlphaGeometry repo](https://github.com/google-deepmind/alphageometry); [rules.txt](https://raw.githubusercontent.com/google-deepmind/alphageometry/main/rules.txt)). AlphaGeometry solved **25/30** IMO-AG-30 problems against Wu's 10 ([DeepMind](https://deepmind.google/discover/blog/alphageometry-an-olympiad-level-ai-system-for-geometry/)). HAGeo reached **28/30** with hand-written heuristics for auxiliary points, and one summary says it needs no neural network ([arXiv 2512.00097](https://arxiv.org/abs/2512.00097v1)), which matters for a browser tutor without a model. Newclid adds the metric concepts (segment length, Pythagoras) that school calculation problems need ([arXiv 2411.11938](https://arxiv.org/abs/2411.11938)). FormalGeo supplies **88 predicates, 196 theorems**, and 6,981 problems annotated with theorem sequences ([arXiv 2310.18021](https://arxiv.org/pdf/2310.18021)), which are ready-made expected-step test fixtures.

Three consequences follow for the rewriting core. First, the geometry engine is a sibling of the algebra rewriter, not an extension of it. Points are atoms, equal lengths and angles become union-find merges, parallel lines are classes of directions, and angle and ratio arithmetic is a Gaussian-elimination side table. Most geometric terms are flat, so a full e-graph's congruence closure adds little, and egglog lacks proof extraction anyway ([export.arxiv.org 2501.02413](https://export.arxiv.org/pdf/2501.02413)). Second, both engines need the same **justification records** (rule id, premises, conclusion), which argues for generalizing `Step` now. Algebra steps are a linear chain of `before → after`. Geometry steps form a DAG of `{statement, reason, premises[]}`, and their numeric sub-problems (solve `x + 2x + 30 = 180`) nest the existing algebra `Step` trees. Third, the rule-record shape (id, message, guard, purpose, buggy flag) should be shared, so that diagnosis, hints, granularity filters and knowledge tracing work across both domains. For diagrams, JSXGraph is pure JavaScript under MIT/LGPL, while GeoGebra's API requires a commercial agreement for commercial use ([JSXGraph](https://github.com/jsxgraph/jsxgraph); [GeoGebra License](https://geogebra.org/license)).

## A five-layer architecture reached in six behavior-preserving phases

| Layer | Responsibility | Built from |
|---|---|---|
| Rules | `{id, message, lhs/rhs or fn, where, purpose, kind: 'normal' \| 'buggy'}`. The message is type-checked against `Step['message']` | Existing transforms, wrapped first and then rewritten as patterns |
| Matcher | Patterns over the Semantic AST with segment variables, opt-in commutativity, a permutation cap, and an index keyed on node type | Custom TypeScript, about MatchPy/SymbolicUtils semantics but much smaller |
| Strategies | Combinators with fuel caps; `named` builds the `substeps` tree; lazy `allfirsts` stream | Stratego/Ideas vocabulary as a TypeScript library |
| Oracle | `equivalent(a, b)`, `ready(expr)`, `similar(a, b)` via canonical polynomial form plus randomized rational evaluation; optional TypeScript e-graph later | Separate module, never emits steps |
| Services | `derive` (today's `solveProblem`), `nextStep`/hints, `diagnose(prev, student)`, granularity filter | Derived from strategies and rules |
| Geometry (later) | Fact store, union-find, angle/ratio linear table, forward-chaining rules with justifications | AlphaGeometry `rules.txt` and FormalGeo theorems, ported |

The migration keeps the existing test suite green at every phase. **Phase 1** builds the combinator library and re-expresses the current loop exactly, `repeat≤10(bottomup(repeat≤10(choice(...))))`, with existing transforms passed in as opaque rules. Snapshot tests should show identical step trees. **Phase 2** adds test-time verification that does not depend on the engine. This includes a property test that every strategy terminates within N steps on random expressions, a visited-hash cycle detector of the kind mathjs uses ([mathjs simplify.js](https://github.com/josdejong/mathjs/blob/develop/src/function/algebra/simplify.js)), and an oracle check that `before ≡ after` for every emitted step. It also includes a **sampled critical-pair test**: generate terms on which two rules both fire, normalize both results, and report pairs whose normal forms differ. This captures most of the value the earlier Knuth–Bendix analysis identified, without symbolic AC unification. Add a weight-decrease assertion for rules tagged `simplify`, in the spirit of CortexJS's cost gate ([CortexJS types](https://github.com/cortex-js/compute-engine/blob/main/src/compute-engine/types-kernel-evaluation.ts)). **Phase 3** switches to the teaching strategy, `repeat(oncebu(...))` split into named phases, and replaces the ordering comments with explicit guards such as "`addNegToSub` only when no distribution applies." This is the one phase that deliberately changes the order of steps, so review the snapshot diffs by hand. **Phase 4** converts simple transforms (`dropAddIdentity`, `removePowOne`, `mulByZeroIsZero`, `distribute`, the power rules) to declarative patterns and keeps the algorithmic ones as function rules. It then re-expresses `solve-linear`'s move-terms and both-sides transforms as a labelled strategy (simplify sides → move variable terms → move constants → divide), so that equation solving and simplification share one engine. **Phase 5** adds `diagnose` and hints on top of `allfirsts`, with five or so curated buggy rules and final-answer search for combined steps. **Phase 6** generalizes `Step` to carry `premises` and adds the geometry fact engine, beginning with angle chasing and congruence, the textbook-named subset of the DD rules. A small TypeScript e-graph is an optional branch from Phase 5 onward, justified only if the canonical-form oracle fails on real inputs (rational expressions, radicals).

Several things remain uncertain. No source measured how readable e-graph proofs are to students, no published numeric cost model for choosing pedagogical steps was found, and the exact Ideas combinator semantics were not verified against primary text. Phases 1–4 do not depend on any of these. Phase 5's diagnosis quality does, and should be validated against real student data before it is relied on.

## Conclusion

Steps in a tutor are a policy, while equivalence is a fact, and the two need different machinery. The current solver mixes them inside one ordered array. Separating them makes the solver more predictable, and it also produces a solution generator, a step checker, a hint ladder and a granularity control from one set of rules and strategies, which is exactly what Ideas showed. The same split also makes geometry tractable. Geometry's readable proofs come from forward saturation with justifications rather than from rewriting toward a normal form, so the reusable investment is the shared rule record and justification-carrying `Step`, not any single engine.

The practical implication is that the first deliverable should be a few hundred lines of combinators that reproduce today's behavior exactly, plus a test harness that checks termination, cycles, step soundness and sampled confluence. The test harness alone would expose every hidden ordering dependency in the 18 current transforms. That makes the later move to explicit guards, declarative patterns and a geometry engine a series of reviewable refactors instead of a rewrite.
